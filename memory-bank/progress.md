- Reporte técnico — Fase 1 (pipeline de análisis, rama Company's-Telemetry-–-Technical-Report):
  - `services/telemetry/analysis.py`: pipeline operacional siguiendo la receta `cargar (SQL) → refinar (Pandas) → convertir tipos → agrupar → agregar → servir` (tele-report.md §Fase 1). 6 funciones de métrica independientes y puras `(session, start_date, end_date) -> list[dict]`:
    1. `events_per_day` — volumen diario de eventos (pulso básico del sistema).
    2. `events_per_type_per_day` — volumen diario por `event_type`.
    3. `error_rate_daily` — tasa de errores diaria sobre `api_response_error_recorded` usando el `level` derivado en ingesta (`_derive_level`): 5xx→error, 4xx→warn.
    4. `error_rate_by_type` — tasa de errores agrupada por `event_type`, con `bindparam(expanding=True)`.
    5. `api_errors_by_endpoint` — errores por endpoint extraído de `tags.endpoint` (JSONB), separando `server_errors` (level=error/5xx).
    6. `auth_failure_rate_daily` — tasa de fallos de login diaria sobre `login_failed`/`login_succeeded`.
    Totalmente vectorizado (sin `.apply(axis=1)` para flags derivados): `level.isin(ERROR_LEVELS)`, `df.groupby().agg()`. Helpers internos `_rows_to_dataframe` (convierte `timestamp` con `pd.to_datetime(utc=True)` antes de todo groupby temporal), `_extract_tags` (dimensión de JSONB), `_to_records` (serie JSON-serializable). `build_telemetry_report(session, start, end) -> dict` agrega las 6 métricas en un solo JSON (contrato para el endpoint de Fase 2).

- Reporte técnico — Fase 2 (endpoint de reporte + cache + dashboard, misma rama Company's-Telemetry-–-Technical-Report):
  - `services/api/cache.py`: nueva instancia `telemetry_report_cache = TTLCache(default_ttl=60.0, name="telemetry_report")` + constante `CACHE_KEY_TELEMETRY_REPORT = "telemetry:report:"` (reutiliza el mecanismo de cache in-memory TTL ya existente para incidencias/proveedores).
  - `services/api/routes/telemetry.py`: nuevo endpoint `GET /telemetry/report` (autenticado con Bearer, igual que incidents/suppliers). Comportamiento:
    - Parámetros opcionales `start_date` / `end_date` (ISO 8601); resuelve la ventana **una sola vez** con `_resolve_period` (inicio inclusivo / fin exclusivo, UTC). Por defecto últimos 7 días UTC. `now` se trunca al minuto (`_round_to_minute`) para que la ventana por defecto sea estable dentro del TTL de 60 s — sin esto cada request generaba una cache key distinta (microsegundos) y el cache era inútil.
    - Llama a `services.telemetry.build_telemetry_report(session, start, end)` (el pipeline de Fase 1) — el endpoint NO calcula métricas; solo resuelve la ventana, ejecuta el pipeline y cachea.
    - Cache: clave `telemetry:report:<start_iso>|<end_iso>` en `telemetry_report_cache`; TTL 60 s → si se pide la misma ventana dentro del TTL devuelve el resultado en cache sin recalcular.
    - Respuesta Pydantic `TelemetryReportResponse`: `{"period": {"from", "to"}, "metrics": {...}}` (6 métricas). `TelemetryPeriod` usa `from_` con alias `from` (`populate_by_name=True`).
    - Errores: `422` si `start_date >= end_date`; `503` si `DATABASE_URL` no está configurada (telemetry_engine None). Import del pipeline vía namespace package con `REPO_ROOT = parents[3]` añadido a `sys.path`.
  - `services/api/tests/test_report.py`: 14 tests → 14/14 passing. Cubren: helpers `_resolve_period` (ventana 7d por defecto, truncado al minuto, fechas explícitas normalizadas a UTC, ventana inválida → error), estructura de respuesta (period + metrics), ventana por defecto pasada al pipeline, fechas explícitas llegando al pipeline, cache (misma ventana → 1 sola llamada), cache expirado → recalcula, ventana distinta → recalcula, ventana inválida → 422, sin DB → 503, sin token → 401.
